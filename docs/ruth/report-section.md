# Authorization and role-based access control — report contribution draft

The DAM application already implemented Admin, Editor and Viewer roles, but its access rules were inconsistent. Baseline API tests showed that an editor's request to change another uploader's asset returned HTTP 200. Viewer requests to delete a tag or an asset version returned HTTP 204. These observations demonstrated horizontal access-control failure between editors and vertical access-control failure from a read-only role. The affected resources included shared asset metadata, the classification dictionary and version records. Baseline provenance is recorded in the supporting evidence; additional source-review concerns are distinguished from independently reproduced vulnerabilities.

The selected policy combines roles with ownership and approval state. Approved assets are intentionally shared among active signed-in users. Editors can upload assets and submit modifications to their own assets; admins publish changes, manage classification data and manage application accounts. Pending and rejected versions are visible only to admins and the editor who owns the asset. Ownership is established by the server's `uploaded_by` assignment, rather than a client-supplied identifier. This design follows least privilege and checks authorization on each protected route, consistent with OWASP authorization guidance [1].

Reusable permission classes now enforce valid active roles, administrative actions and ownership. The API uses the current database user role, so changing a browser role value or retaining a JWT issued before demotion does not restore privileges. User management now checks the DAM admin role consistently instead of relying on Django's separate staff flag. REST requests cannot assign system-level flags such as `is_superuser`, groups or Django permissions. Additional checks protect superuser accounts and prevent an administrator from deleting or removing their own access through the API. Django admin model access is also restricted to application administrators, preventing a staff editor with model permissions from using an alternative interface.

Object checks alone do not protect collections or nested representations. Django REST Framework documents that list visibility and creation need explicit handling [2]. Therefore, asset and version querysets filter inaccessible records, and nested version serialization applies the same visibility policy. Protected file endpoints use these filters before opening storage. Uploader representations expose only an identifier and username rather than unnecessary account details. Unauthorized draft identifiers return HTTP 404, while authenticated users attempting forbidden role actions receive HTTP 403. Anonymous protected-resource requests return HTTP 401.

Editor `PUT`, `PATCH` and explicit update requests now enter the same pending-approval workflow. Changes do not mutate the currently approved asset before review. Direct version creation and replacement routes are disabled, and approval requests accept only a status transition on a pending version. Parent-asset legacy uploads cannot provide an alternative ownership bypass. Asset-row locks serialize version numbering, and an older pending version cannot be approved over newer published content. A replacement image is optional for metadata-only edits: the existing stored file is retained, while editor changes still require approval. A file remains mandatory for an initial upload.

Verification includes positive and negative tests for all three roles, separate editor owners, anonymous requests, role changes, version visibility, protected downloads and alternate HTTP methods. Tests also confirm that approved shared downloads, legitimate owner submissions and admin actions continue to work. Metadata-only tests exercise editor submission through approval and confirm that the file is preserved. The accompanying verification summary and JUnit XML contain the actual execution results. Audit fixtures were corrected to meet existing category validation and ownership requirements, then retested to check integration with Member 5's logging controls.

The controls address the chosen shared-asset policy; they do not implement private asset sharing or tenant isolation. Local preview runs over HTTP and is not evidence of Member 4's secure deployment. Automated tests reduce regression risk but do not establish that every possible attack is absent. The group should repeat manual browser/API testing and integration review before submission. Ruth should review this section, understand each control and use only results supported by the submitted evidence.
